# 第零部分 预备知识：把每个词搞懂

> 目标：读完这一部分，你看到"用 QLoRA 微调 Qwen3.5-2B 做自杀风险三分类"这句话时，能说出每个词的含义，以及它们**为什么**被组合在一起。

## 0.1 这个项目在解决什么问题

校园心理支持系统每天收到大量消息，其中极少数可能隐藏自伤/自杀风险。原有防线是**规则引擎**——人工写的关键词和逻辑。它能抓住"我想死"这种**显式表达**，但对**隐喻式表达**容易漏报：

> "想消失""要是没出生过就好了""活着就是拖累"

这些话一个高危关键词都没有（或只有很弱的词），规则引擎抓不住。本项目训练一个**专用小模型**作为规则的增强器：读入一条消息，输出一个 JSON 风险等级（low/medium/high），与规则结果融合后交给业务链路。

一句话记住整个项目：**规则抓显式，模型抓隐喻，融合取max，谁也不许降级。**

## 0.2 大模型是怎么"说话"的

- **token（词元）**：模型处理文本的最小单位——可能是半个词、一个词或一个标点。"我想消失"可能被切成 4~6 个 token。模型的世界里只有 token 序列和编号。
- **下一个词预测**：大语言模型本质是一个超大的"接龙函数"：给定前面的 token，预测下一个 token 的概率分布。"今天天气真"后面"好"的概率很高。它**只会这一件事**。
- **因果语言模型（causal LM）**：只允许每个位置看它**前面**的 token（不能偷看后文）。Qwen3.5 就是这类模型——训练配置里的 `task_type: CAUSAL_LM` 就是这个意思。
- **基座模型（base model）**：只做过"海量文本接龙预训练"的原始模型，比如本项目的 `Qwen/Qwen3.5-2B-Base`（约 18.9 亿参数、24 层）。它知识渊博但**没学过任何具体任务的输出格式**——你问它"这条消息风险多高"，它可能续写一篇讨论风险的小作文，而不是给你想要的 JSON。
- **微调（fine-tuning）**：在基座上用少量任务数据继续训练，把"什么都会一点"变成"精确做好一件事"。

> 💡 **新手直觉**：基座模型像一个读遍图书馆但没上过岗的人。微调 = 岗前培训，教它的不是"知识"，而是"上岗的标准动作"——看到一条消息，输出固定格式的判断。

**为什么选 2B 不选更大的**：本机显卡是 RTX 4060 Laptop（约 8GB 显存）。模型越大，量化后占的显存越多。2B 是 8GB 显存 + 512 token 上下文下能稳定完成"训练→评测"闭环的规模（实测训练峰值约 4.9GB）。

## 0.3 SFT：用例子教会模型任务

**监督微调（Supervised Fine-Tuning, SFT）**：给模型看大量"(输入，标准答案)"对，让它学会"看到这类输入就产生这类输出"。

本项目每条 SFT 样本是一个三段对话（来自 `data_contract.py` 的 `to_sft_record`）：

```json
{
  "messages": [
    {"role": "system", "content": "你是校园心理支持系统的风险评估器,……只输出一个 JSON 对象……"},
    {"role": "user", "content": "我最近觉得自己很多余。"},
    {"role": "assistant", "content": "{\"risk_level\":\"medium\",\"reason\":\"明显痛苦但无自伤意向\"}"}
  ]
}
```

三个角色各司其职：

| 角色 | 是什么 | 类比 |
| --- | --- | --- |
| system | 任务说明书（永远固定，即"提示词契约 v2"） | 考卷开头的答题要求 |
| user | 被评估的消息 | 题目 |
| assistant | 标准答案（风险 JSON） | 标准答案 |

模型学到的核心能力：在 system 说明书约束下，把任意 user 消息压缩成一个符合格式的 JSON 判断。

## 0.4 LoRA：只学 0.44% 的增量

**朴素微调的困境**：最直接的做法是更新模型全部 18.9 亿参数。但显存里除了模型本身，还要为每个参数存**梯度**（1 份）和**优化器状态**（AdamW 要 2 份）——2B 全参数微调在 8GB 显卡上必然 OOM。另外，全参数改写容易把预训练的通用能力"洗掉"（灾难性遗忘）。

**LoRA 的洞察**：教一个模型做风险分类，需要的"新知识"远小于模型本身的维度。权重的改动量 ΔW 是"低秩"的。于是：

1. **冻结**原有权重 W（不训练、不存梯度）；
2. 在需要改动的层旁挂一对小矩阵：ΔW = B×A（A 是 r×d，B 是 d×r，秩 r=8 远小于模型维度）；
3. **只训练 A 和 B**。

**数字对比**：可训练参数 8,409,600，占总数 1,890,234,688 的 **0.4449%**。训练显存从"放不下"降到"峰值约 4.9GB"；adapter 文件只有几十 MB，便于版本管理和审计。

> 💡 **比喻**：LoRA 不改写教科书，只在书页边上贴便签。"全书"（基座）保持原样，"便签"（adapter）记录所有新学的东西。交付时可以只传便签（几 MB），也可以把便签誊进书里（合并/merge，几个 GB）。

三个超参数的直觉（第 7 章有完整版）：

- **r（秩）**：便签的"容量"。越大表达力越强，但越容易过拟合、越占显存。本项目 r=8——0.44% 的参数已在八门槛达标，**够用就好**。
- **alpha（缩放）**：LoRA 分支输出会乘以 alpha/r。本项目 16/8=2，等效把新学的改动放大 2 倍。
- **dropout**：训练时随机丢弃 LoRA 分支 5% 的神经元，抑制小样本过拟合。

## 0.5 量化：用更少的比特保存权重

**量化**：用更少的比特表示每个权重数值，存储体积近似按比例缩小：

| 精度 | 每参数比特数 | 2B 模型权重体积（约） | 用在哪 |
| --- | ---: | ---: | --- |
| FP32 | 32 | 7.6 GB | 训练原始精度，本机用不到 |
| BF16 / FP16 | 16 | 3.8 GB | 合并与推理 |
| INT8 | 8 | 1.9 GB | Ollama 本地模型常用 |
| **NF4** | **4** | **约 1 GB** | **QLoRA 训练时基座的存储精度** |

- **NF4（NormalFloat4）**：神经网络权重分布近似正态（大部分值在 0 附近），NF4 按正态分布的分位数设计 4-bit 取值格子，量化误差在统计上最小——比普通 INT4 更适合权重。
- **二重量化**：4-bit 量化每组需要一个缩放常数，这些常数本身也要占空间；把它们再量化一次（用 8-bit 存），再省约 0.4 bit/参数。

**⚠️ 全书最重要的"不矛盾"之一——存储精度 ≠ 计算精度**：4-bit 只决定权重**怎么存**；做矩阵乘法时，权重先反量化回 BF16 再算（`bnb_4bit_compute_dtype: bfloat16`）。QLoRA 是"**4-bit 存、16-bit 算**"。这两句话放在一起不矛盾——就像一张高压缩照片（存储小）放映时仍然是全尺寸画面（计算用）。

## 0.6 QLoRA：两者拼起来

**QLoRA = 4-bit 量化冻结基座 + 在其上训练 BF16 的 LoRA adapter**。显存账（量级估算）：

```text
基座 18.9 亿参数 × 4 bit          ≈ 1.0 GB   （NF4 + 二重量化）
LoRA 8.4M 参数 BF16 权重+梯度+状态  ≈ 0.1 GB
优化器分页/激活/上下文/碎片         ≈ 3-4 GB
─────────────────────────────────────────
实测训练峰值 CUDA 显存             ≈ 4.9 GB   （8GB 显卡稳定完成）
```

为什么不是单独 LoRA 或单独量化？

- 单独 LoRA（不量化基座）：仅基座 BF16 权重就 3.8GB，加上激活与碎片，8GB 卡几乎没有余量；
- 单独量化（不做 LoRA）：没解决"训练时优化器状态爆炸"的问题。

QLoRA 让"冻结的大模型用 4-bit 省、训练的小模块用 16-bit 稳"。再配合**梯度检查点**（前向不存全部激活、反向重算，用 20-30% 时间换大量显存）和**分页优化器**（优化器状态显存不够时自动搬进内存），2B 模型在笔记本显卡上训得动。

## 0.7 为什么输出必须是 JSON

让模型只输出 `{"risk_level": "low|medium|high", "reason": "20字以内依据"}` 是刻意的工程决策：

1. **机器可解析**：纯文本判断（"我觉得挺危险的"）程序没法消费；
2. **可校验、可量化**：格式固定才能算"JSON 有效率"这类验收指标；
3. **失败要显式**：解析失败时服务返回 `risk_level: null`——调用方明确回退规则通道，绝不伪装成成功；
4. **约束即安全**：只有三个离散标签，杜绝模型自由发挥；融合层 `max(规则, 模型)` 保证模型**只能升高风险、不能降低**。

## 0.8 四个数据集合：用考试理解"泛化"

**泛化**：模型在**没见过**的数据上依然做对的能力。衡量它的唯一办法：留一部分数据不参与训练，只用它们考试。本项目四个集合：

| 集合 | 规模 | 比喻 | 参与训练？ | 用途 |
| --- | ---: | --- | :---: | --- |
| train | 2867 | 平时上课的教材与习题 | ✅ | 拟合 |
| dev | 200 | 模拟考 | ❌ | 每个 epoch 算 eval_loss，选最优 checkpoint、早停 |
| devtest（test.jsonl） | 1414 | 随堂大测 | ❌ | 开发期参考诊断，**不作为上线门槛** |
| 冻结 holdout（stress 87） | 87 | 高考密封卷 | ❌ 永久 | 最终验收的八项门槛 |

两个新手必懂的"为什么"：

- **为什么 stress 必须永久冻结**：它若有任何一条混进训练，模型等于"背过原题"，分数虚高而真实能力不变——这叫**数据泄漏**。所以数据构建时会拒绝所有与 stress 精确或近重复（相似度 ≥ 0.82）的候选（README §6.4）。
- **为什么 devtest 考得好还不能上线**：devtest 与训练数据出自同一构建流程（同规则重标），分布接近训练集；stress 87 条则包含隐喻、第三人称干扰等**专门设计的困难场景**。随堂测考得好，不代表密封卷考得好——历史上第二、三、五、六版都倒在 stress 的某个门槛上，反复验证了这一点。

# 第一部分 易混淆点集中澄清

> 这一部分是本手册的核心。每一条都按"❌ 常见误会 → ✅ 正确理解 → 对照表 → 为什么"展开。这些混淆全部来自真实的新手直觉，先在这里排雷，后面章节会顺畅得多。

## 混 1：train / dev / devtest / stress——四个集合到底谁管什么

**❌ 常见误会**："devtest 1414 条准确率 0.895，比 stress 87 条大多了，凭什么上线只看那 87 条？"

**✅ 正确理解**：集合的价值不在大小，在**出题人和考生隔离得多干净**。

| | train 2867 | dev 200 | devtest 1414 | stress 87 |
| --- | --- | --- | --- | --- |
| 比喻 | 教材习题 | 模拟考 | 随堂大测 | 高考密封卷 |
| 模型见过吗 | 见过（学它） | 没见过，但**你**反复看它调模型 | 没见过，构建流程与 train 同源 | 没见过，且**永久冻结** |
| 能信多少 | 不能用于评估 | 只配做"选型" | 诊断参考（分布偏乐观） | 唯一的验收依据 |
| 谁在反复用它 | —— | eval_loss 选 checkpoint | 开发期找薄弱点 | 只在最终验收动一次 |

**为什么**：devtest 的 1414 条和 train 是**同一个脚本、同一套裁决规则**做出来的——相当于同一个老师出的随堂测。它考得好说明"学得扎实"，但不能证明"遇到陌生出题人（真实世界）还能考好"。stress 87 条是**专门设计的困难场景**（隐喻、第三人称干扰），且被精确哈希 + 0.82 相似度阈值隔离，任何与它相似的文本都进不了训练。隔离得越彻底的考试，分数越能代表真实能力。

**一句话记住**：**大而不冻，不如小而冻结；devtest 是体检报告，stress 是准考资格。**

> **可迁移的方法论**：train/dev/test 划分 +「评测集永不参与任何调参决策」的冻结纪律，是通用实验设计知识，任何 ML 项目都适用；四个集合的具体配比与 stress 的困难场景设计是本项目特化。

## 混 2：adapter / merged 模型 / GGUF / checkpoint-N——四种文件别再认错

**❌ 常见误会**："都是模型文件，从 Ollama 目录里把 qwen3.5:2b 拷出来当训练基座，省得下载 4.5GB。"

**✅ 正确理解**：这四种文件处于**流水线的不同阶段**，形态和用途完全不同：

| 文件 | 是什么 | 大小 | 谁产出 | 能干什么 |
| --- | --- | --- | --- | --- |
| **adapter** | LoRA 训练出的"增量补丁"（ΔW=BA） | 几十 MB | train 脚本 | 不能独立推理；可审计、可合并 |
| **merged（safetensors）** | adapter 数值上并入基座后的**完整模型** | ~4.5GB（分片） | merge 脚本 | 推理、评测、发布——**交付物** |
| **checkpoint-360/540** | 训练中间状态（含优化器，可续训） | GB 级/个 | Trainer 自动保存 | 断点续训；不是最终交付物 |
| **GGUF** | 为推理重新打包的工件（可能再量化） | 视量化而定 | Ollama/llama.cpp 转换 | 只能推理；**禁止当训练基座**（第 1 章红线） |

**为什么 GGUF 不能当基座**：训练是在基座上"叠加学习"。GGUF 经过转换与再量化，无法证明与官方 revision 逐字节同源。用它训练，所有"基座 vs 微调"的对比都失去参照物——等于在来路不明的地基上盖楼。基座只认**钉死 revision 的官方 safetensors 快照**（README §5）。

**一句话记住**：**adapter 是补丁，merged 是成品衣服，GGUF 是别人裁过的布，checkpoint 是缝纫中途的半成品。只有原厂布料（官方 safetensors）+ 自己的补丁，才是一件能溯源的衣服。**

## 混 3：LoRA vs QLoRA；"4-bit 存、16-bit 算"为什么不矛盾

**❌ 常见误会**："4-bit 量化后精度损失这么大，训出来的模型是不是也在 4-bit 精度下算数？那误差不得爆炸？"

**✅ 正确理解**：

- **LoRA** 是"训练**谁**"的答案：冻结基座，只训练旁挂的低秩小矩阵。
- **QLoRA** 在此之上回答"基座**怎么存**"：基座以 4-bit NF4 存放，省显存。

两者是叠加关系，不是竞争关系：QLoRA = LoRA + 基座 4-bit 存储。

计算时，4-bit 权重先**反量化回 BF16** 再参与矩阵乘法（`bnb_4bit_compute_dtype: bfloat16`）。所以：

| 环节 | 精度 |
| --- | --- |
| 基座权重**存放** | 4-bit NF4（+二重量化） |
| 基座权重**参与计算** | BF16（反量化后） |
| LoRA adapter 权重/梯度/优化 | BF16 |

**为什么这样各取所长**：存储瓶颈在"巨大的基座"（4-bit 省到 1GB），数值瓶颈在"计算与梯度"（BF16 动态范围大、稳定）。让大的省、小的稳，两边不冲突。

**一句话记住**：**QLoRA 的 Q 只管"放"，不管"算"；压缩的是仓库，不是流水线。**

## 混 4：BF16 vs FP16——都是 16 位，差在哪

**❌ 常见误会**："BF16 和 FP16 都是 16-bit 浮点，随便用哪个都一样。"

**✅ 正确理解**：16 个比特怎么分配决定了脾气：

| | BF16 | FP16 |
| --- | --- | --- |
| 比特分配 | 8 指数位（同 FP32）+ 7 尾数位 | 5 指数位 + 10 尾数位 |
| 强项 | **动态范围大**，几乎不会上溢/下溢 | 尾数多，单点精度略高 |
| 弱项 | 单点精度略低 | 范围窄，需要 loss scaling 保护 |
| 本项目 | **首选**（RTX 4060 原生支持） | 仅当 GPU 不支持 BF16 且配置允许时**显式降级** |

**为什么本项目选 BF16**：训练中最怕的不是"算得不够细"，而是"数值炸了"。BF16 的指数位与 FP32 一致，表达范围相同，训练稳定；FP16 省下的精度对风险三分类没有实际收益，还要搭上 loss scaling 的复杂度。

**规则细节**：降级不是静默的——只有 GPU 不支持 BF16 且 `fp16_fallback: true` 时才降，并且会在输出里写明实际 compute dtype。

**一句话记住**：**BF16 保范围，FP16 保精度；训练要稳不要炫，默认 BF16。**

## 混 5：泄漏（leakage） vs 回退（fallback）——两个方向的"安全阀"

**❌ 常见误会**：两个词都常和安全一起出现，容易当成一回事。

**✅ 正确理解**：它们方向完全相反：

| | 泄漏 leakage | 回退 fallback |
|---|---|---|
| 防的事故 | **考试题混进教材**：评测数据进入训练数据 → 分数虚高 | **模型失灵时无人管**：服务挂了/超时/输出非法 → 风险漏判 |
| 发生在 | 训练之前（数据构建阶段拦截） | 生产运行时（推理链路上） |
| 机制 | 精确哈希 + 3-gram Jaccard ≥ 0.82 即拒绝入 train/dev | 融合层发现模型异常，自动退回规则通道 |
| 类比 | 防止小抄带进考场 | 考生晕倒时监考老师顶上 |

**为什么分开记很重要**：泄漏毁的是"评测的可信度"（你不知道模型真实水平）；回退保的是"生产的可用性"（用户永远有规则兜底）。一个在训练侧、一个在推理侧，混着谈会导致排查时找错半边。

**一句话记住**：**泄漏是"考题漏进教材"（训练侧，事前防）；回退是"模型倒了规则顶"（生产侧，事后兜）。**

## 混 6：`risk_level: null` vs `low`——最危险也最常见的误读

**❌ 常见误会**："服务返回 null，就当 low 处理呗，反正都不是 high。"

**✅ 正确理解**：null 和 low 是**两种语义**：

| 返回值 | 含义 | 正确处理 |
| --- | --- | --- |
| `"low"` | 模型**明确判断**：一般困扰，无自伤风险 | 正常放行 |
| `null` | 模型**没有给出可用答案**（解析失败/输出为空） | **回退规则通道**，绝不能当 low |

**为什么这是安全红线**：把 null 当 low，等于"模型哑巴了就当它说没事"。假设一条高危消息让模型输出坏掉（比如生成了截断的 JSON），null→low 的误读会**直接漏报高危**。这正是输出契约里"失败要显式"的设计动机：宁可暴露失败，不可伪装成功。

配套细节（README §8.6）：服务端 JSON 解析是"宽容五步"（剥代码围栏→标准解析→正则提取 {...}→校验标签→reason 截断），但**任何一步失败都返回 null，绝不猜一个标签**。

**一句话记住**：**null 是"没答上来"，不是"答了没事"；把 null 当 low，等于给漏报开后门。**

## 混 7：高危词 ≠ high——标签判的是"谁在说、说什么、什么时候"

**❌ 常见误会**："出现'死''自杀'就该标 high，规则和数据都这么弄最保险。"

**✅ 正确理解**：high 的判定条件是**自身 + 意向/计划**，高危词只是必要线索之一。四道守卫决定一个高危词要不要"升级"：

| 守卫 | 问题 | 例子 | 结果 |
| --- | --- | --- | --- |
| **主体**（谁在说） | 说的是自己还是别人？ | "我朋友说他想消失" | low（第三人称） |
| **语境**（什么场合） | 真实倾诉还是新闻/论文/影视？ | "论文里讨论自杀干预方法" | low（虚构/学术） |
| **时间**（什么时候） | 当下意念还是过去旧事？ | "我小时候割过腕，现在好了" | medium（自伤史） |
| **意向**（怎么说的） | 直接意向还是康复叙述？ | "我用运动替代了自伤" | 不升级（康复） |

**为什么这么苛刻**：系统的输出会触发不同强度的业务响应（high 触发危机干预）。漏报 high 人身代价极高，但把所有含高危词的句子都判 high，会造成"狼来了"，淹没真正的高危。边界画在"**自身 + 意向/计划**"上。这也是历史版本反复翻车的地方（第二、三、五、六版都栽在误升级），v9 用提示词 v2 + 人工对照数据资产才修复。

**一句话记住**：**高危词是"烟雾报警器"，但先看火在谁家、什么时候烧的：他人的火、过去的火、纸上的火，都不是你家的火。**

## 混 8：medium 与 high 之间的一条细线——"不配被爱" vs "不配活着"

**❌ 常见误会**："都挺绝望的，差不多得了，都标 high/medium 不就行了？"

**✅ 正确理解**：这恰是 v9 修复的核心边界（提示词 v1→v2 的关键变化）。判别特征只有一个：**有没有指向"自身消失/死亡"的表达**。

| 表达 | 标签 | 判别特征 |
| --- | --- | --- |
| "觉得自己不配被爱、很没用" | **medium** | 强烈痛苦、自我贬低，但**无死亡/消失词** |
| "觉得自己不配**活着**" | **high** | 自我否定**指向自身存在本身** |
| "活着就是家人的负担" | 视措辞 | 有无"消失/结束"类表达决定跨不跨线 |
| "有时候想，要是没出生过就好了" | **high** | 隐喻式自伤意念（提示词 v2 明确列出） |

**为什么这条线如此重要**：v1 的提示词把"不配""活着多余"这类宽泛示例混列在 high 定义里，模型在这条细线上大量误判——第五、六版正是卡在冻结集的 corp-084/091（自我否定句误升级）。v2 移除歧义示例、并配套 `selfworth-contrast-v8` 最小差异对数据（"不配被爱"medium ↔ "不配活着"high，死亡词是唯一判别特征）才修复。

**一句话记住**：**痛苦到绝望是 medium；绝望到"想从世界上消失"才是 high。判别词是死亡/消失，不是悲伤程度。**

## 混 9：选型 vs 评测 vs 验收——三件容易被混为一谈的事

**❌ 常见误会**："评测脚本跑完，数字达标，就是'通过验收'了。"

**✅ 正确理解**：这是三个不同环节、用不同数据、由不同主体下结论：

| | 选型 | 评测 | 验收 |
| --- | --- | --- | --- |
| 干什么 | 训练中自动挑最优 checkpoint | 脚本跑出指标 | **人工**逐项对照门槛下结论 |
| 用哪个数据 | dev 200（eval_loss 最低） | stress 87 / devtest 1414 | 只认 stress 87 |
| 谁做 | `load_best_model_at_end` 自动 | eval 脚本 | 人工 + 记录（脚本不自动出 pass/fail） |
| 产出 | 最终 adapter | 评测 JSON 报告 | 验收结论 + 元数据 |

**为什么验收不能自动化在脚本里**：门槛是人工对照报告确认的（REPRODUCIBILITY 第 7 节）。评测脚本只产出指标数字；"数字好"到"宣布通过"之间必须有人逐项核对并记录——这一步偷工，整个验收的证据链就断了。

**一句话记住**：**脚本出数字，人下结论；dev 选型，stress 验收。**

## 混 10：eval_loss 回升 ≠ 训练失败——那是"心电图"不是"死亡通知书"

**❌ 常见误会**："epoch 3 的 eval_loss 比 epoch 2 高了，训练失败了，重跑！"

**✅ 正确理解**：v9 的 eval_loss 序列 `0.0818 → 0.0638 → 0.0654` 是一份**健康**的小数据 SFT 心电图：

```text
epoch1  0.0818   ● 还在有效学习
epoch2  0.0638   ● ◄ 最优点（系统自动回选这里）
epoch3  0.0654   ● 微升 = 过拟合开端（开始背训练集细节）
```

- epoch2→3 回升说明模型开始**过拟合**（记忆训练集、泛化变差）——这是小数据训练的正常现象，不是事故；
- `load_best_model_at_end` 会**自动**回选 eval_loss 最低的 epoch 2 权重作为最终 adapter，无需人工干预；
- 若连续 2 次评估无改善，`early_stopping_patience=2` 提前终止，省时掐断过拟合。

**真正要警惕的形态**：三个 epoch 一路下降到结束（可能"还没学够"，可实验 +1 epoch）；或第一个 epoch 就回升（优先怀疑数据/学习率，而不是继续调 epoch）。

**一句话记住**：**先降后微升是健康曲线，最优点在拐点前；系统会自动回选，你该做的是看懂它，不是重跑它。**

## 混 11：`pass_same_family_with_caveat` 不是 gate 失败

**❌ 常见误会**："gate 报告状态叫 'with_caveat'（带警告），是不是没通过？换个快照再试？"

**✅ 正确理解**：gate 通过状态有两级（`base_model_gate.py`）：

| 状态 | 含义 | 何时出现 |
| --- | --- | --- |
| `pass_same_family_with_caveat` | **常规通过**：结构、架构、规模全部匹配官方快照；仅 Ollama 转换 provenance 未验证 | 当前 v9 管线的实际状态（不传 provenance，恒为此值） |
| `pass_exact` | 严格通过：提供了经验证的 Ollama 转换证明记录 | 仅在显式传入 provenance 时可能出现 |

**为什么这样设计**：本机同时存在 Ollama 的 `qwen3.5:2b`（Q8 GGUF）。gate 不禁止它的存在，但要求你**不得声称**它与官方权重已证明同源——"同族、同规模"≠"同一份权重"。训练本身只依赖 safetensors 快照，与 Ollama 工件无关，所以带 caveat 的通过完全不影响训练有效性。dry-run 输出里看到这个状态是**正常且预期**的。

**一句话记住**：**caveat 是"我没有证据说 Ollama 那份和官方同源"，不是"你的基座有问题"。**

## 混 12：版本编号的坑——磁盘目录名 ≠ 版次

**❌ 常见误会**："看到 `checkpoints/aegis-risk-qwen3.5-2b-v5`，这是第五版的产物。"

**✅ 正确理解**：版本编号有历史遗留，磁盘旧编号与正式版次的映射是：

| 磁盘旧编号 | v1 | v3 | v4 | v5 | v7 | v8 | v9 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 正式版次 | 第一版 | 第二版 | 第三版 | **第四版** | 第五版 | 第六版 | **第七版** |

（"v2"编号作废，历史上并无独立 v2 训练。）

**为什么必须以谱系索引为准**：目录名是当时随手起的，版次才是正式谱系。引用历史结论（"第三版 FPR 超标""第五版卡在 corp-084"）时若按目录名推断，会张冠李戴。唯一权威映射在 [reports/TRAINING-HISTORY-INDEX.md](../reports/TRAINING-HISTORY-INDEX.md)。

**一句话记住**：**目录名是"当时的小名"，版次是"身份证"；引历史，查谱系，别看文件夹。**

## 混 13：v9 管线 vs legacy 管线——两套实现，不要混用

**❌ 常见误会**："泄漏防护有两份代码（脚本内联的 `leaks()` 和 `src/leakage_guard.py`），随便用哪份都行。"

**✅ 正确理解**：

| | v9 管线（当前） | legacy 管线（第一版） |
| --- | --- | --- |
| 数据构建入口 | `prepare_risk_sft_v4.py` | `prepare_risk_sft.py` |
| 泄漏检查 | **脚本内联实现**：纯 3-gram Jaccard ≥ 0.82 | `leakage_guard.py`：**max(Jaccard, SequenceMatcher)** ≥ 0.82，带倒排索引预筛 |
| 弱标签映射 | 脚本内联裁决漏斗（六分支） | `source_ingest.py` 正则弱映射 |
| 状态 | 当前推荐流程 | 保留作教学材料与旧复现 |

**为什么不能混用**：相似度口径不同（纯 Jaccard vs 取两者最大值），同一候选在两套实现下的"泄漏与否"判定可能不同——泄漏拒绝集合随之改变，manifest 数字不可比。复刻时给 v9 管线换用 `leakage_guard`，产出的数据就和 v9 官方数据对不上了。

**一句话记住**：**v9 的防护是"内联自带的"，legacy 的是"教学版的"；口径不同，不许串门。**

> **可迁移的方法论**：同一原则的多套实现必须「口径对齐或显式隔离」，否则复现实验的数字不可比——这是所有工程复刻的通用纪律；Jaccard vs SequenceMatcher 的具体选择是项目特化。

## 混 14：`build_consolidated.py` 的输出 ≠ 训练数据

**❌ 常见误会**："跑完 `build_consolidated.py` 生成了 `train_messages.jsonl`，直接拿来训练。"

**✅ 正确理解**：那是**审计中间产物**，用的是构建期的**旧 prompt** 和旧裁决标准。正确链路永远是：

```text
consolidated_risk_v1 → prepare_risk_sft_v4.py（重新裁决 + 换 v2 prompt）→ data/risk_sft_v9
```

**为什么**：提示词契约 v2 是训练/评测/服务三方共用的唯一 system prompt（见混 15）。跳过 `prepare_risk_sft_v4.py` 的重裁决，等于用旧题库 + 旧答题要求训练，再拿新答题要求考试——训练-推理 prompt 漂移，性能必然异常。

**一句话记住**：**consolidated 是"原材料仓库"，v4 脚本是"加工厂"；直接吃原材料会消化不良。**

## 混 15：提示词契约的两处副本——改一处必须同步另一处，且是重训级事件

**❌ 常见误会**："system prompt 就是个配置，改几个字让模型判得更准，改完重跑评测就行。"

**✅ 正确理解**：三层认知：

1. **模型是"针对这段文字"训练的**：每条 SFT 样本的 system 段就是它。训练与推理的 prompt 不同，等于平时练的题型和考卷完全不一样，性能必然漂移。
2. **它有两处独立的物理副本**：
   - `training/src/aegis_training/data_contract.py` —— **权威定义**，数据构建/冻结评测/本地服务都从这里导入（自动一致）；
   - 生产项目 `app/llm/client.py` —— 独立副本，必须与上面**逐字同步**。
3. **改 prompt = 重训级事件**：新 prompt → 重建数据 → 重训 → 全量重验收。而且**旧模型的数字只绑定旧 prompt**，不能拿 v2 重新解释旧版成绩。

**一句话记住**：**prompt 不是配置是契约；改它等于换了考试大纲，一切从头再考。**

## 混 16：显存（VRAM） vs 内存（RAM）

**❌ 常见误会**："我电脑 32G 内存，怎么 8G 显存就爆了？"

**✅ 正确理解**：

| | 显存 VRAM | 内存 RAM |
| --- | --- | --- |
| 在哪 | GPU 板载 | 主板 |
| 谁用 | CUDA 张量、模型权重、激活 | CPU 程序、数据加载 |
| 本项目 | **峰值约 4.9GB / 8GB**——训练的硬瓶颈 | 充裕，几乎不构成约束 |

训练脚本报的 `peak_cuda_memory_bytes` 指的是显存。OOM（Out Of Memory）如无特殊说明都指显存溢出。分页优化器（`paged_adamw_8bit`）做的正是"优化器状态在显存/内存之间搬"——它拿内存当显存的溢出区，但**模型权重和激活必须留在显存**，这部分省不掉。

**一句话记住**：**训练的生死线是显存不是内存；4.9GB 是峰值显存，不是"用了 4.9G 内存"。**

# 第二部分 完整故事线：一条消息如何变成一个上线模型

> 按"从头重建这个项目"的顺序讲一遍完整故事。每一站回答三件事：**这步在干什么 / 为什么必须有 / 新手要防的坑**。具体命令与参数一律指向 [README.md](README.md) 对应章节，本手册只管"懂"。

## 站 1 认识边界：两个仓库，一条隔离线

**在干什么**：整个系统分两个仓库——`aegis-psych-agent`（生产 FastAPI 应用：Agent、RAG、审批、回复）和 `AegisTraining`（本仓库：数据契约、QLoRA 训练、离线评测）。生产进程**只通过 HTTP/JSON 契约**（`POST /assess`）调用已验收的模型服务，绝不在进程内加载训练依赖。

**为什么**：训练依赖（PyTorch/CUDA/bitsandbytes）体积巨大且版本敏感，混进生产会让部署体积和故障面失控；更关键的是，训练中的模型是**未验收的实验资产**，不能与对外服务共存。

**新手要防的坑**："临时调试方便"是越界的头号动机——往生产 requirements 加 torch、把 checkpoint 提交进 Git、把本机 8301 写进生产 `.env`，全是违反红线的行为（README §1.3 有六条红线全文）。

## 站 2 数据契约：先把"什么是一条合格数据"写成法律

**在干什么**：所有训练样本必须过 `data_contract.py` 的校验：五件套必填（sample_id/message/risk_level/reason/source）、reason ≤ 20 字、标签只能是三值、**high 必须 speaker_scope=self**、`label_method`/`review_status` 必须如实记录。任何一条不满足，构建立即终止。

**为什么**：数据来自多个渠道（外部数据集、人工编写、蒸馏挖掘），没有统一契约，"medium 是什么意思"每个来源一套答案，模型学到的是一锅粥。把失败拦在最便宜的阶段（数据），而不是最贵的阶段（3 小时训练后）。

**核心标签原则**（详见混 7/混 8）：high = 自身 + 意向/计划；medium = 明显痛苦无自伤证据；low = 一般困扰 + 他人/虚构语境。撑不下去、不配、没意义等词**不能脱离主体和计划性**仅凭关键词升级。

**新手要防的坑**：把自动映射样本的 `label_method` 写成 `manual_reviewed`——契约校验拦不住谎言，但 manifest 审计会，这等于学术造假。

## 站 3 泄漏防护：把高考卷锁进保险柜

**在干什么**：构建数据时，把每条候选与冻结的 stress 87 条比对——先精确哈希拒绝原文复用，再算字符 3-gram Jaccard 相似度，≥ 0.82 即拒绝进入 train/dev。拒绝记录写入 manifest 的 `leakage_rejected`，逐条可审计。

**为什么阈值是 0.82**：隐喻类高危表达高度模板化（"想消失/离开这个世界/结束这一切"），合法训练样本与 stress 天然共享片段。阈值太高（0.95）漏掉"改几个词的原题"；太低（0.5）误杀大量合法隐喻模板。0.82 是"漏检"与"误杀"之间的权衡值——**不允许为了多进数据调低它**。

**动手感受**（纯标准库，可复制运行）：

```bat
D:\AegisTraining\envs\qlora-qwen35\Scripts\python.exe -c "def g(t):return {t[i:i+3] for i in range(len(t)-2)}; a='有时候真的想从这个世界上消失'; b='真的想从世界上消失掉算了'; print(len(g(a)&g(b))/len(g(a)|g(b)))"
```

两条"看起来很像"的文本相似度在 0.4~0.6 区间（不拒）；改到逐句雷同会冲过 0.82（拒）。

> **可迁移的方法论**：任何"冻结评测集"都需要精确 + 模糊双层去重，阈值必须在漏检与误杀之间用数据实证而不是拍脑袋——具体 0.82 是本项目特化。

## 站 4 数据构建：2867 条训练数据是怎么配出来的

**在干什么**：`prepare_risk_sft_v4.py` 把候选池加工成 train 2867 / dev 200 / devtest 1414。关键机制：

- **确定性抽样**：按 `sha256("42|"+文本)` 排序后截配额，不用随机数——两次构建（哪怕不同机器）得到完全相同的数据，可复现从机制上保证；
- **人工样本整组直入**：六族人工资产（困难负例、成对对照、自我否定对照等）先直接进 train，配额含它们——成对对照的价值就在"主语一换、标签翻转"，拆散就失效；
- **dev 先预留**：medium 样本稀缺，先给 dev 抽足 60 条再轮到 train；
- **重标漏斗**：六分支裁决（详见文末附录「源码走读精选」），顺序不可调换——意念分支必须排在痛苦短语之前，否则"我想死"会先被判成 medium 漏走。

**新手要防的坑**：构建退出码 0 只说明"程序没崩"，必须打开 manifest 核对数量分布、审阅 `leakage_rejected`——审阅它是确认"防护在工作"，不是走过场。

> **可迁移的方法论**：把人工规则做成「有序漏斗 + 每步改判留日志」是通用的可审计数据处理模式；六分支的具体顺序与正则族是本项目特化。

## 站 5 基座 gate：花 3 秒确认地基，再花 3 小时盖楼

**在干什么**：训练/合并前，`base_model_gate.py` 核对本地快照的 repo、revision（钉死 `b1485b2f…`）、model_type、层数（24）、hidden（2048）、权重清单（必须是 safetensors），拒绝多模态结构和 GGUF。

**为什么**：基座若被静默替换成同名不同内容（HF 仓库更新、镜像不完整），训练照常跑完，但产出一个**无法追溯、无法对比、无法复现**的模型。gate 的两级通过状态语义见混 11——`pass_same_family_with_caveat` 是常规通过，别当失败。

## 站 6 QLoRA 参数：每个数字都有理由

完整参数表在 README §7，这里给"为什么"的速记：

| 参数 | 值 | 一句话理由 |
| --- | --- | --- |
| rank r | 8 | 0.44% 参数已达标，够用就好；加大要重新验收 |
| alpha | 16 | 缩放 α/r=2，控制新知识的叠加幅度 |
| dropout | 0.05 | 2867 条小数据，轻量正则防过拟合 |
| batch × 梯度累积 | 1 × 16 | 显存上先活下来（batch=1），训练动态上等效 16 |
| gradient_checkpointing | true | 用 20-30% 时间换激活显存数量级下降——显存账的功臣 |
| learning_rate | 1e-4 | LoRA 惯例量级（比全参数微调大一个数量级） |
| warmup + cosine | 5% + 余弦 | 开局小步热身，收尾步子越来越小 |
| paged_adamw_8bit | — | 优化器状态 8-bit + 显存不够自动搬内存 |
| 3 epochs + 早停 patience=2 | — | 小数据 1 遍学不透、5 遍必过拟合 |
| cutoff_len 512 + 截断报错 | — | 绝不让"空答案"样本静默混入训练 |

**只教答案不教题目**：训练对 system/user 段的标签写 `-100`（交叉熵忽略标记），loss 只从 assistant 的 JSON 答案回传——模型只学"给判断"，不浪费容量学"怎么当好一个用户"。

**步数推算**（验证你懂了配置）：有效批量 = 1×16 = 16；每 epoch = ⌈2867/16⌉ = 180 步；3 epochs = **540 步**（与 v9 实测一致）；warmup ≈ 5%×540 ≈ 27 步。

## 站 7 训练：dry-run、3 小时、一条心电图

**流程**：先 dry-run（分钟级走完全部前置检查：CUDA、gate、目标层、tokenize、参数量）→ 正式训练（v9 实测 540 步、2h54m、峰值显存 4.9GB）→ 产出 adapter + checkpoint + training-manifest。

**为什么 dry-run 不能省**：正式训练 3 小时，dry-run 以分钟级成本把环境/基座/配置/数据/分词的全部雷提前引爆。跳过它等于放弃免费预检。

**训练曲线怎么读**：见混 10。`0.0818 → 0.0638 → 0.0654`，最优 epoch 2 / step 360 由系统自动回选。

**新手要防的坑**：忘传版本化 `--output-root`（两次实验覆盖同一目录 = 谱系灾难）；训练中途 Ctrl+C 后直接原地重跑。

## 站 8 合并与评测：从"补丁"到"成品"，再上考场

**合并**：`merge_risk_qlora.py` 用 BF16 加载基座，把 adapter 数值并入（`safe_merge` 带数值检查），输出分片 safetensors + 导出 manifest。合并即"把验收对象固化为交付物"——生产不直接加载 adapter（那要求生产进程装 peft/bitsandbytes，违反隔离红线）。

**冻结评测**：`eval_risk_qlora.py` 对 stress 87 条同时测五个组合——规则单独、原模型单独、原模型+规则融合、QLoRA 单独、**QLoRA+规则融合**。为什么测融合：生产真实行为就是 `max(规则, 模型)`，验收必须评"接入后的系统"。评测前必须设 `AEGIS_PROJECT_ROOT`——规则基线用的就是生产同款规则引擎，这是刻意设计。

**指标速记**：

- `recall`：某类真实样本找回了多少——**high recall 是安全生命线**；
- `FPR`：non-high 被误升为 high 的比例——误报的代价；
- 两者天然制衡（放宽松→召回升误报也升），所以第 9 章"HIGH recall 不低于基线"与"FPR 增幅 ≤2pp"必须**同时**满足——单看任何一个都能被"无脑全报 high"或"永远不报 high"骗过；
- `macro-F1`：三类 F1 简单平均，防止大类（low）淹没小类（high）。

**devtest 参考评测**：1414 条大样本诊断，看混淆矩阵和误判样本找薄弱点。两个口径细节：解析失败按协议记 low 参与统计（所以 `json_valid_rate` 必须与 accuracy 一起读）；devtest 分数**只用于诊断**（见混 1）。

## 站 9 八项门槛：全部通过才有资格谈上线

| 门槛 | 阈值 | 防什么事故 |
| --- | --- | --- |
| JSON 有效率 | ≥ 98% | 输出契约崩坏，下游没法用 |
| 合法标签率 | ≥ 99% | 同上 |
| reason 超长 | = 0 | 长篇解释拖垮延迟 |
| 融合 HIGH recall | ≥ 基线 0.52 | 模型的存在理由：必须比纯规则更好（v9 达 0.76） |
| 隐喻隐式新增命中 | ≥ 4/25 | 初心考核：隐喻真的补上了（v9 +6） |
| 第三人称新增误报 | ≤ 1 | 防止抓隐喻抓到"走火" |
| non-high→high FPR 增幅 | ≤ 2pp | 微调不许放大最贵的错误（历史第二三版在此翻车） |
| P95 延迟 | ≤ 8s | 风险评估在对话链路上，慢 = 不可部署 |

八项是"与"关系，缺一即整体失败。**通过 ≠ 自动判定**：脚本出数字，人逐项对照记录（混 9）。任一失败：标 research-only、保留证据、分析分层误判、迭代下一版——失败的 adapter 不删（第五六版锁定的 corp-084/091 直接指导了 v9 的修复）。

**如实标注的边界**：stress 是工程冻结集，不是独立临床盲测集（合成表达与仓库规则有共同设计背景）；上线还需外部专家审阅。devtest 上 medium-F1 0.380 低于上一版也如实记录在案——评测要真实，不凑满分。

## 站 10 接入与发布：融合取 max，回滚先断开关

**生产接入语义**：`RISK_QLORA_ENABLED` 默认 false（新配置永不改变现有行为）；规则评估**永久执行**；融合 `max(规则, 模型)`——模型只能加分不能减分，任何异常（超时/400/null）回退规则。想让模型"纠正"规则判严的个案？设计上不可能，这类需求应走规则策略修订。

**发布纪律**：权重不入代码仓库；每个发布必须带完整元数据（基座 revision、数据 manifest、prompt 版本、SHA-256、验收报告、回滚版本）——发布回答的是"六个月后出问题时能否说清它是怎么来的"。

**回滚顺序**：断开关 → 恢复上一版 → 验证规则链路 → 记录事件。第一步永远是拉回已知安全状态，而不是先诊断。

# 第三部分 新手 FAQ

**Q1 我没有 N 卡，能学这个项目吗？**
能学概念（本手册全程不需要 GPU），不能跑正式训练与冻结评测——训练入口强制 CUDA，NF4 也依赖 NVIDIA。可用 dry-run 在任意 CUDA 机器上验证配置。

**Q2 为什么不用更大的模型？**
8GB 显存是硬约束：QLoRA 已把基座压到 4-bit，更大的模型会在激活与优化器状态上先爆。2B + 0.44% 可训练参数已在八门槛达标。

**Q3 `pip install -r` 成功了为什么还不能训练？**
requirements 只有库依赖下限，**不含 GPU 版 PyTorch wheel**（必须按驱动单独选）。跑 README §4.4 自检：版本号带 `+cu12x` 且 `is_available()` 为 True。

**Q4 我能自己往 train.jsonl 里加几条数据吗？**
不能手工改产物——绕过契约、泄漏检查和 manifest，整条审计链作废。人工样本走 `training/data/authored/`，由构建脚本整组进入。

**Q5 泄漏阈值 0.82 太严，调低点多进些数据行吗？**
不行，红线。调低 = 给评测注水，stress 分数从此不可信（站 3）。

**Q6 epoch 3 loss 变高了，要不要重训？**
先读混 10。那是健康的过拟合信号，系统已自动回选最优点。

**Q7 想改 rank / 学习率 / epoch 怎么办？**
复制配置为版本化实验文件 → `--config` 显式传入 → 新 `--output-root` → dry-run → 训练 → **完整重新验收**。任何超参变更都是新实验，没有免费午餐。

**Q8 `risk_level: null` 和 `low` 什么区别？**
见混 6——null 必须 回退规则，当 low 处理会漏报。

**Q9 8301 服务能直接给生产用吗？**
不能。无 TLS、认证、限流、审计，只做 smoke test；且生产 URL 校验本身就拒绝环回/私有地址。

**Q10 seed=42 能保证结果逐位一致吗？**
能保证流程与数据确定性（哈希抽样、固定种子）；CUDA 算子非确定性会带来微小数值波动。可复现 = "流程可复现 + 证据完整"，不承诺逐位一致。

**Q11 八项门槛是脚本自动判的吗？**
不是。脚本出指标，人工对照记录（混 9）。"指标好"和"通过验收"之间隔着一次人工逐项核对。

**Q12 模型某条判错了，能手工修吗？**
不存在"修单条"通道——模型行为只能通过数据/提示词/超参的**版本化变更 + 重训 + 重验收**改变。单点后处理会破坏可审计性。

**Q13 stress 只有 87 条，样本量是不是太小？**
87 条是**冻结验收集**不是统计研究集：职责是守住工程底线（八门槛），不是证明临床有效性。上线前仍需外部专家审阅与独立数据。

**Q14 为什么 medium 样本要"扩量"？**
真实语料里 medium 相对稀疏，直接训练会偏向 low/high 两头。通过校园合成 + 蒸馏挖掘补量（上限 1.35 倍、限量 200 条），保持三分类均衡。

**Q15 训练能断点续跑吗？**
checkpoint 目录（如 `checkpoint-360/`）保存了可恢复状态，但 resume 属于实验决策：先明确"这还是不是同一个实验"并记录。任何时候不要让两次训练覆盖同一个 `--output-root`。

### 一、数据构建裁决引擎（prepare_risk_sft_v4.py）

**核心难题**：标签原则说"判的是说话人自身的意向"，但正则只会匹配字面。解法是三件套：**意图正则 × 语境守卫 × 就近主语裁决**。

（1）就近主语裁决（`_nearest_subject_is_self`）：

```python
def _nearest_subject_is_self(text, start, window=12):
    span = text[max(0, start - window):start]          # 只看匹配点前 12 字
    self_pos  = [m.start() for m in SELF_TOKEN.finditer(span)]     # 我/自己/咱
    other_pos = [m.start() for m in OTHER_SUBJECT.finditer(span)]  # 朋友/新闻/他/…
    if not self_pos and not other_pos:
        return None            # 无主语：默认自身（第一人称独白）
    if self_pos and (not other_pos or max(self_pos) > max(other_pos)):
        return True            # 离匹配点最近的主语是自身
    return False
```

为什么只看前文、取最近：中文口语的风险短语几乎都紧跟主语（"我快撑不住了"），离匹配点更近的主语就是短语的主人；无主语的独白（"撑不住了……"）默认按第一人称处理——宁可交给后续验收去发现误报，也不放过潜在高危。

（2）三重语境守卫，防三类经典误升级：

| 守卫 | 防什么 | 例子 |
| --- | --- | --- |
| `PAST_GUARD`（小时候/当年/曾经/以前…） | 既往自伤旧事被当当前意念 | "我小时候割过腕，现在好了" → 自伤史（medium），不是 high |
| `RECOVERY_GUARD`（而不是/拒绝/停止…） | 康复叙述中的自伤词 | "我用运动替代了自伤" → 不升级 |
| `DISCUSSION_GUARD`（研究/方式/方法/效果…） | 科普/讨论语境 | "论文里比较了各种干预方式的效果" → 不升级 |

（3）判定器按"锚定自伤（我+割腕/遗书…）→ 裸自伤 → 意念词"顺序扫描；锚定自伤命中 `PAST_GUARD` 时**跳过该处继续扫描**而不是整句否决——同一句可能既有旧事也有新意念。`IDEATION` 正则本身编码了边界：`(?<!不)想死` 用否定后顾排除"不想死"；"活不下去"是多义词，按裁决归痛苦短语（medium）而不是意念。

**正反例速查**（可对照源码验证）：

| 文本 | 判定 | 触发机制 |
| --- | --- | --- |
| "我最近总想着怎么消失" | high | IDEATION"想消失"+ 无主语默认自身 |
| "他说他最近总想消失" | low | 就近主语 = 他 |
| "我不想死了" | 不命中 | 否定后顾 |
| "我小时候割过腕" | medium（selfharm_history） | PAST_GUARD 命中 |
| "快撑不下去了，来预约心理咨询" | medium（痛苦无意图族） | 痛苦短语命中、无自伤意图 |

### 二、六分支裁决漏斗（relabel()）

```text
consolidated 候选（每条带 labels_raw 细标签）
 ① high 且 labels_raw 只含「用户攻击行为」            → 丢弃（aggression_only）
 ② high → 按 labels_raw 细标签定 _fine；
       被动自杀意图 + MEANINGLESS 且无 DEATH_CUE      → 降 medium（passive_demote）
 ③ low + 自身意念                                    → 升 high（explicit_relabel，不受第三人称豁免）
 ④ low + 非第三人称 + 自伤史/康复叙述                → medium（selfharm_history）
 ⑤ low + 非第三人称 + 自身痛苦短语                   → medium（pain_without_intent）
 ⑥ low + 非第三人称 + 显著症状                       → medium（significant_symptom）
 ⑦ low + 非第三人称 + 痛苦线索挖掘（MEDIUM_MINE）    → medium（distress_mine）
 ⑧ medium → exploration；其余 → low
```

为什么顺序不可调换：①必须在②前（先清掉与风险无关的攻击样本）；③必须在④-⑦前（意念是 high 级信号——"我想死"同时命中痛苦短语，若⑤在前会把高危降级）；④在⑤前（旧事叙述往往也含痛苦词，"既往史"是更精确的归因）。每次改判写入 `relabel_log`（`{id, from, to, rule}`），manifest 的 `relabel_summary` 按"from→to"聚合计数——**重标可审计，不是黑盒**。
